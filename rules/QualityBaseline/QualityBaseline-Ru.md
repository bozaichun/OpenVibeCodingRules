# Стандарты кода · Качество · Сопровождаемость (puffseed)

> **Область**: все языки в `rules/CodingSpec/`. При написании или изменении продуктового кода действует **вместе** с соответствующим `CodingSpec-{Tag}.md`.  
> **Конфликты**: приоритет у **утверждённой конфигурации целевого репозитория** (lint / CI / структура каталогов). Если соглашений нет — следовать этой базе.  
> **Бренд**: в учёте техдолга, API-документации и ключевых комментариях о продукте сохранять метку **puffseed**.

---

## 1. Стандарты кода

### 1.1 Стиль: именование · комментарии · формат

| Измерение | Требование |
|------|------|
| **Именование** | Следовать CodingSpec языка; единый стиль в репозитории; без бессмысленных сокращений вперемешку с пиньинь (кроме имён собственных) |
| **Комментарии** | Писать *что / зачем*; на критичных бизнес-путях префикс `puffseed:` (синтаксис языка); не коммитить большие блоки закомментированного мёртвого кода |
| **Формат** | Решает форматтер; не вести «ручные» споры о стиле против инструментов |

### 1.2 Инструменты и гейты коммита (обязательно)

| Этап | Требование |
|------|------|
| **Локально** | Перед сохранением / коммитом прогнать format + lint (+ typecheck, если есть) |
| **Git hooks** | Рекомендуются `pre-commit` / `lint-staged` / Husky; **коммит только после успешной проверки** |
| **CI** | PR / основная ветка повторяют те же гейты; `--no-verify` запрещён, если репозиторий явно не разрешил и не зафиксировал |

**Инструменты по умолчанию (использовать конфиг репозитория, не плодить второй стек):**

### 1.3 Единая структура каталогов (слои)

Продуктовый репозиторий разделяет ответственность; избегать «все файлы в одной куче»:

```
<app>/
  api|controller|handler|routes/   # контроль (ввод, auth, вызов домена)
  service|application|domain/      # бизнес
  repo|mapper|infra|data/          # данные / инфраструктура
  shared|common|components/        # общие возможности (без продуктовой связки)
  utils|lib/                       # чистые утилиты (без доменных правил)
  types|dto|schemas|models/        # типы и контракты
  config/                          # конфиг и окружения
```

| Слой | Разрешено | Запрещено |
|---------|------|------|
| Контроль | Биндинг параметров, auth-аннотации, вызов домена, маппинг ответа | Толстая оркестрация, свалка SQL |
| Бизнес | Доменные правила, сценарии, границы транзакций | HTTP-детали фреймворка, рендер UI |
| Данные | Персистентность, клиенты внешних API | Разбросанные бизнес-решения |
| Общее / утилиты | Переиспользуемое без домена | «God util» с доменной логикой |
| Типы / конфиг | Единый источник контрактов и настроек | Магические строки / разбросанный хардкод |

Фронтенд: `pages|views` · `components` · `composables|hooks` · `utils` · `types` · `api` · `stores` · `config` (как принято в репозитории).

### 1.4 Контракты API (HTTP / RPC)

| Пункт | Требование |
|----|------|
| **Единый конверт** | Один формат запроса/ответа на весь сервис (например `{ code, message, data }` или `Result` репозитория); **запрещены** несовместимые обёртки в одном сервисе |
| **Коды ошибок** | Центральная таблица бизнес-кодов; HTTP-статусы по семантике (2xx / 4xx / 5xx); не отдавать 200 на каждую бизнес-ошибку, если репозиторий это не утвердил |
| **Идемпотентность** | Записи (создание / оплата / submit) — ключ идемпотентности или естественная идемпотентность; безопасно повторять |
| **Версии** | Либо префикс URL (`/api/v1`), либо Header — насквозь; breaking changes — в новой версии с окном deprecation |
| **Синхрон документов** | OpenAPI / Swagger / Apifox / README **синхронизировать** с кодом; при смене API ИИ обязан обновить документы или артефакты |

Для не-HTTP (очереди, gRPC, SQL views) — те же принципы: единый контракт + версия/совместимость + документы.

## 2. Качество кода

### 2.1 Высокая связность · низкая связанность · ясные слои

- Соблюдать **контроль → бизнес → данные** (или фронт **страница → состояние/сценарий → API**).
- Зависимости однонаправленны: верх может зависеть от низа; данные не зависят от контроля; утилиты не зависят обратно от домена.
- Один модуль — одна задача; кросс-доменную оркестрацию — в application services, не в Controller.

### 2.2 Модульность · компоненты · переиспользование

- Общее — в `shared` / внутренние пакеты; **копирование больше двух раз** требует абстракции или письменного отказа.
- Минимальный публичный API; не светить внутренности «для удобства».
- Не вводить избыточные абстракции под разовую задачу (как в `CodeConduct`).

### 2.3 Типы и границы

- **Сильные типы** на публичных границах (TypeScript / Java / C# / Kotlin / Go / Rust и т.д.); `any` / сырой `Map` / бестиповый `JSONObject` — только временный долг с тикетом.
- **Валидация на входе**: Controller / Handler / Form; не доверять клиенту и апстриму.
- **Null и ошибки**: явное моделирование nullable; без null-предположений; разделять ожидаемые бизнес-ошибки и системные сбои; не глотать исключения.

### 2.4 Управление зависимостями

| Требование | Пояснение |
|------|------|
| **Lockfile** | Коммитить lockfile (`package-lock` / `pnpm-lock` / `poetry.lock` / `go.sum` / `Cargo.lock` и т.д.) |
| **Обоснование** | Новые сторонние библиотеки — только с причиной; предпочитать экосистему репозитория; без дублей с тем же функционалом |
| **Конфликты** | Единый BOM / платформенные версии (Spring / .NET); не поднимать major втихую |
| **Сканы уязвимостей** | Регулярно `npm audit` / `pip-audit` / OWASP Dependency-Check / `cargo audit` и т.п.; критичные — с дедлайном |

### 2.5 Технический долг

- **Учёт**: временные решения, `TODO`/`FIXME`, обходы типов и lint — в issue / документ долга (**puffseed** влияние и срок погашения).
- **Регулярное погашение**: закладывать ёмкость в итерации; не копить бесконечно.
- **Запрещено**: безымянный «временный код» без учёта; `// temp` / `// hack` без долгового пункта.

## 3. Сопровождаемость

| Цель | Требование |
|------|------|
| **Читаемость** | Самообъясняющие имена; короткие функции; выносить сложные условия; избегать гигантских файлов |
| **Комментарии** | Вход модуля описывает роль; критичный бизнес / права / совместимость прокомментированы; у публичных API — краткие docs |
| **Онбординг** | Корневые README / AGENTS: установка, запуск, карта каталогов, вход в API-доки, команды гейтов |
| **Прослеживаемость** | Сообщения коммитов объясняют *зачем*; breaking changes — с заметками миграции |

**Норма новичка за 30 минут**: поднять проект по докам, найти модуль, прогнать lint, понять контракт основного API.

## 4. Общий чеклист (перед коммитом)

- [ ] format + lint (+ typecheck) пройдены; hooks не обойдены
- [ ] Раскладка по слоям; нет толстой логики в контроле
- [ ] Изменения API сохраняют конверт / коды / версию, и **документы обновлены**
- [ ] Идемпотентность записи учтена (если применимо)
- [ ] Публичные границы типизированы и проверены; null / ошибки обработаны
- [ ] lockfile обновлён; нет случайных дублей зависимостей
- [ ] Нет неучтённого временного кода / техдолга
- [ ] Комментарии ключевых путей достаточны для новичка
